the problem

How a good epic goes wrong.

You already know this story. You have lived it.

Eleven agents, one shared folder

Everyone builds in the same checkout. Two agents touch the same file, one overwrites the other, and the third runs a build against half-applied changes.

“It's done”

An agent says the work is green. You merge. CI goes red on something the agent never ran — and now five people know the merge was premature.

Where were we?

The epic's state lives in a chat that scrolled away. Tomorrow, a new session starts from zero: which issues are blocked, which have PRs, which were abandoned mid-build.

The merge stampede

Four green PRs, merged in the wrong order. The conflict lands after the fact, the fix goes in on top of it, and the diff that nobody reviewed becomes the diff that ships.

setwave exists so that story ends: one issue, one worktree, one agent — and a script that refuses every step you have not approved.

inside a wave

The walls, in three columns.

What an agent in a setwave wave can reach, what it can never touch, and what happens only on your word.

Inside the wave

  • Its own worktree, at its issue's branch, born from origin/base
  • The issue body and its comments — premises included, with permission to correct them
  • The repo's real gate, read from CI or the manifest — never invented
  • A judge over its diff, before any merge
  • Sibling issues warned when its PR changes symbols they cite

Out of reach

  • Your main checkout — never worked in, refused when dirty
  • Force push, auto-merge, branch deletion — not a flag, an absence
  • Other agents' worktrees and build directories
  • AI attribution in any commit or PR body
  • The chat as storage — state lives in GitHub and git

Only on your OK

  • The merge — one PR at a time, for the pinned delta
  • The plan — base SHA and every head; anything moved, it asks again
  • Issue creation — a refinement session authors locally; wave plan is the only door
  • Reopening a closed epic — refused; the flag is yours to pass

poka-yoke

It prefers making the wrong action impossible.

What cannot be made impossible is made loud. These refusals are code, not advice — each one pinned by a test that fails when the guard is removed.

no --yes, no merge

The OK was for that delta: base SHA and every PR head pinned. Anything moved → re-plan and ask again.

JUDGE-MISSING · JUDGE-FAIL · JUDGE-STALE

The producer never grades its own PR. An independent read-only judge must pass the exact head being merged.

LEDGER-MISSING · LEDGER-MISMATCH

Every PR carries the issue's Done-when ledger. Merge applies it to the issue — the next agent receives only what remains.

VERSION-OUTSIDE-RELEASE

The version line changes only in a PR titled “Release …”. Feature PRs that bump it are refused.

agent-exhausted

Three resumes without a new commit exhaust an agent. The fourth dispatch is refused; the escalation is commented on the issue and the epic. Nothing closes by itself.

attribution · forbidden git · secrets

Fail-open guard hooks deny AI attribution, destructive git commands and secret reads before they happen — install with one command.

what it is not

Honest boundaries.

Not autonomous

No agent merges anything. The loop stops at your OK — every time, on every wave, in every repo.

Not a scheduler

Nothing runs in the background while you sleep. A wave runs when you run it, and the run log says what happened.

Not a CI replacement

The gate comes from your CI or your manifest. setwave reads the truth; it does not become it.

Not GitHub-only forever

The state model is sub-issues + blocked_by. That is the whole model — other trackers are a different plugin.

any repo · any account · any stack

The prompt is the same line tomorrow.

/setwave:wave <epic>

The data comes from GitHub and git at run time — so the same words work in the next session, the next wave, the next repo, the next account.

questions people ask

Before you ask.

What happens when two PRs conflict?

Predicted before the merge: wave order runs pairwise git merge-tree and a chain simulation that names the PR that will turn red. When it still lands, wave resolve merges the base into the PR's branch in its own worktree, runs the gate, and pushes normally — a conflict stops with file and line ranges for you, and --continue refuses leftover markers.

Does it only work on Rust repos / my stack?

Any stack with a gate: the commands are read from your CI workflow or from the manifest (Cargo, package.json, pyproject, go.mod, Makefile). Stdlib Python is the only runtime dependency on your machine besides gh and git.

Can an agent go rogue and merge something?

The merge path is wave merge, and it re-runs verify and the judge check itself before each PR. Agents have no merge command in their prompt, fail-open hooks deny destructive git, and the guard hooks are installable with one command.

What does it cost in tokens?

Batches of four, not eleven — the same result for a quarter of the tokens, no rate-limit deaths. A dead agent is resumed with its context, never redispatched from zero. Every run is logged, so wave stats answers from data.
